# 技術スタック

## アーキテクチャ

サーバーレスの静的Webアプリケーション。APIサーバーは持たず、設置店舗データは静的ファイルとしてバンドルする。Vercelにデプロイ。

## コア技術

- **言語**: TypeScript
- **フレームワーク**: Next.js (App Router)
- **ホスティング**: Vercel
- **地図API**: Google Maps JavaScript API（またはスマホUXに優れた代替）

## 主要ライブラリ

- 地図描画ライブラリ（Google Maps React wrapper等）
- スタイリング: 軽量CSSソリューション（Tailwind CSS推奨）

## 開発基準

### 型安全性
- TypeScript strict mode
- 店舗データに明確な型定義

### コード品質
- ESLint + Prettier
- Next.js推奨の設定に準拠

## 開発環境

### 必須ツール
- Node.js 20+
- npm / pnpm

### 基本コマンド
```bash
# 開発: npm run dev
# ビルド: npm run build
# リント: npm run lint
```

## 主要な技術判断

- **APIサーバーなし**: ユーザー規模が小さく、データ更新頻度も低いため静的データで十分
- **Next.js選定**: Vercelデプロイとの親和性、SSG対応
- **スマホファースト**: ターゲットユーザーの主要アクセス手段がスマートフォン

## データ管理方針（ランタイムDB 非採用）

設置店舗データは**読み取り専用かつ小規模**であり、更新はビルド前のオフラインパイプライン（GitHub Actions）でのみ行う。アプリ側は生成済みの静的データ（`stores.json`）を read-only で参照するのみで、ランタイムでの書き込みは発生しない。

このデータ特性に基づき、本スペックの範囲では**ランタイムデータベース（Turso 等）を導入しない**。理由は以下のとおり。

- **不要な複雑化の回避**: 読み取り専用データにDBを導入しても、運用・コスト・障害点が増えるだけで利点がない。
- **配信特性との整合**: 静的データはビルド時にバンドルされ、CDNエッジ配信される。エッジ配信の低レイテンシ・高可用性を、ランタイムDB問い合わせで損なわない。
- **鮮度の担保手段が別にある**: データ鮮度は定期実行パイプライン（スクレイプ→マージ→ジオコード→JSON生成）が担保しており、ランタイムでの動的取得を必要としない。
- **バージョン管理**: データの版は生成物に埋め込む `lastUpdated`（最終更新日時）で表現する。DBによるバージョニングは不要。

### 再検討の条件

将来的に**ユーザー投稿・レビュー・お気に入り等の動的データ要件**が発生した時点で、ランタイムデータベース（Turso 等）の採用を改めて検討する。それまでは静的データ方針を維持する。
