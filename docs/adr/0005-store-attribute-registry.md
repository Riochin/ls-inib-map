# ADR-0005: 店舗属性の定義を1か所に集約する（属性レジストリ）

- 日付: 2026-10-10
- ステータス: Accepted（2026-10-10 採用。ver2.6 の先頭で挙動を変えないリファクタとして着手）
- 関連: ADR-0002、ADR-0003、`src/types/store.ts`、`src/types/overrides.ts`、`src/lib/report.ts`、`src/app/api/report/route.ts`、`src/lib/apply-overrides.ts`

## 背景

- 店舗属性を1つ足すと、型・オーバーライド適用・フォーム・API 検証・Issue 本文生成・詳細表示・充実度・絞り込み・自動反映の指示文・各テストと、約25ファイルに手が入る（録画台の追加時の実績）。
- 同じ属性が層ごとに **別の形** で表現されている。
  - 店舗データとオーバーライド: ゲーム別は `hasRecordingByGame: { 'jojo-ls': 'yes' }` のようなマップ
  - フォーム送信と Issue 生成（`StructuredStoreInput`）: `hasRecordingJojoLs` / `hasRecordingGundamExvs` のようにゲームごとに平たく展開した別名フィールド
  - API 検証（`validateStructuredStore`）: フィールドごとに手書きの分岐
  - Issue 本文の提案値表: 「録画台（ラスサバ）」のような日本語ラベルを `buildStructuredStoreIssue` に直書き
- フロアは「両ゲーム同値なら1行、違えば2行」という特別処理が Issue 生成だけにあり、他の属性と規則がそろっていない。
- ver2.6 で無制限台（有無＋台数）、クレジットサービス・貸切（三値＋文章）と3種類の形が増える。この先も項目追加が続く見込みで、「Issue の提案値まわりの型を統一できないか」という要望が出た。

## 決定

店舗属性の定義を `src/lib/store-attributes.ts` の **属性レジストリ** に集約し、報告の入力型・API 検証・Issue 本文・オーバーライド適用・詳細表示・充実度をそこから導出する。

レジストリの1項目が持つもの:

- キー（`Store` / `OverrideEntry` のフィールド名そのまま。例 `hasRecordingByGame`）
- 表示ラベル（例「録画台」。Issue 本文と詳細モーダルで共通）
- 範囲: `store`（店単位）か `game`（ゲーム別）
- 種類: `ternary` / `text` / `number` / `list`、および上限（文字数・個数・数値範囲）
- 付随フィールド: 台数（`unlimitedCountByGame`）や文章（`creditServiceNote`）のように、本体に添える値
- 充実度に数えるか、絞り込みに使うか

導出するもの:

1. **報告の入力型**: `StructuredStoreInput` のゲーム別平坦フィールドを廃止し、`attributes` を `OverrideEntry` と同じ形（ゲーム別はマップ）で持つ。フォーム → API → Issue → 自動反映 → overrides.json が **同じ形** で流れる
2. **API 検証**: 種類と上限から汎用に検証する。属性ごとの手書き分岐をなくす
3. **Issue 本文の提案値表**: レジストリの順にラベルを引いて行を作る。ゲーム別は「ラベル（ラスサバ）」、両ゲーム同値なら1行にまとめる規則を **全属性に** 適用する（フロアの特別処理を一般化）
4. **オーバーライド適用**: `store` は代入、`game` は `mergeByGame`、出どころは属性キーごとに記録。属性ごとの if 文をなくす
5. **詳細モーダル**: レジストリの順に行を描く。表示の整形は種類ごとに1つ
6. **充実度**: フラグの立った属性だけ数える

変えないもの:

- `Store` / `OverrideEntry` のフィールド名と `overrides.json` の中身。既存データはそのまま
- Issue 本文のラベル文字列。過去の Issue と自動反映の指示文に影響しない
- `Store` インターフェース自体は明示的に書き続ける（JSDoc の説明価値が高い）。レジストリのキーが `Store` と `OverrideEntry` の両方に存在することは型レベルで検査する
- フォームの見た目。三値のゲーム別項目（録画台・配信台・無制限台）はレジストリを回して1つの部品で描くが、台数・営業時間・決済・折りたたみは個別に書く。UI の細かさはレジストリで表現しない

進め方: ver2.6 の中で **先にレジストリ化（挙動を変えないリファクタ）**、その後に新属性をレジストリ経由で追加する。リファクタ側は Issue 本文のスナップショットと既存テスト（58 ファイル）で挙動が変わっていないことを確かめる。コミットは「レジストリ導入」「各層の置き換え」「新属性追加」で分ける。

理由:

- 属性追加の作業が「レジストリに1行、`Store` と `OverrideEntry` に型1行、フォームの UI、自動反映の指示文1行、テスト」に縮む。残るのは本当に属性ごとに違う部分だけ。
- 入力から保存までが同じ形になるので、層の間の変換バグ（名前の付け間違い、片方のゲームだけ落ちる）が起きない。
- 自動反映ワークフローの Claude も、提案値表のラベルとフィールド名の対応をレジストリ1ファイルで読める。
- 大がかりな仕組みではない。定義オブジェクト1つと、それを回す関数が数個。

## 検討した選択肢

### 案B: 現状維持（属性ごとに各層へ手で追加する）

- 概要: 録画台を足したときと同じ手順を、無制限台・クレジットサービス・貸切でも繰り返す。
- 利点: リファクタの初期コストがゼロ。各層が素朴で読みやすい。
- 欠点 / リスク: 1属性ごとに約15の実装ファイルを触る。フロアのように層ごとの規則がずれていく。平坦フィールド名（`hasUnlimitedJojoLs` など）が増え続ける。
- 却下理由: 今回3属性、今後も追加が続く見込みで、繰り返しコストが初期コストを上回る。

### 案C: スキーマライブラリ（zod など）で入力型と検証を定義する

- 概要: 属性のスキーマを zod で書き、型推論と API 検証をそこから得る。
- 利点: 検証の記述が短く、エラーメッセージも揃う。
- 欠点 / リスク: 依存が1つ増える。Issue 本文のラベル、ゲーム別の範囲、充実度フラグなど検証以外のメタ情報はスキーマだけでは持てず、結局レジストリが要る。
- 却下理由: レジストリがあれば検証は数種類の素朴な関数で足りる。将来、検証部分だけ zod に載せ替えることは妨げない。

### 案D: 属性定義からフォーム UI も含めて全部自動生成する

- 概要: JSON の属性定義からフォーム・詳細・Issue・検証をすべて生成する。
- 利点: 属性追加が定義1行で完結する。
- 欠点 / リスク: 「あり」のときだけ台数欄を出す、決済を折りたたむ、両ゲーム店だけ2列にする、といった UI の判断を定義言語で表す必要があり、仕組みが肥大化する。属性は10個程度で、汎用化の見返りが小さい。
- 却下理由: 過剰設計。UI は手で書き、データの流れだけをレジストリで統一する。

## 影響

- 楽になる: 属性追加の作業量が約1/3になる。入力から保存まで形が同じなので、自動反映の指示文も「レジストリのラベルどおりに反映」と短く書ける。
- 難しくなる: 各層が「レジストリを回す」間接的な書き方になり、1属性だけ追いたいときに読みにくくなる。レジストリ導入のリファクタに1〜2日分の工数がかかる。API のペイロード形式が変わるため、デプロイ直前に開いていたタブからの送信は失敗する（フォームと API は同時にデプロイされるので、それ以外の互換問題は無い）。
- 見直しの目安: 属性の種類（三値・文字列・数値・リスト）に収まらない属性が出てきたら、レジストリの型を広げるか個別実装にするかを ADR で判断する。
