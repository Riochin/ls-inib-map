# ADR（設計判断の記録）

このアプリの設計判断を、1判断＝1ファイルで残す。「何を選んだか」より **「なぜ他の案を捨てたか」** を残すのが目的。
後から「どうしてこの持ち方なんだっけ」と迷ったとき、会話ログやPRを掘らずにここを読めば分かる状態を保つ。

## 書く対象

次のどれかに当たる判断は ADR にする。

- データの持ち方（型・フィールド・出どころの扱い）
- 層の分け方・責務の置き場所（どのファイルが何を担うか）
- 運用ルール（ワークフロー・レビューの通し方・公開範囲）
- UXの方針で、代替案を比べて捨てたもの

書かないもの: 実装の細部、一時的な作業手順、1ファイルで完結する命名。

## 書き方

1. [template.md](template.md) をコピーし、`NNNN-英語のスラッグ.md` で保存する（番号は4桁の連番）
2. 日付・ステータス・関連リンク（Issue / PR / 実装計画 / モック）を埋める
3. 検討した案は **最低2つ** 書く。却下理由を1行で言えない案は検討不足
4. 下の一覧に1行足す

ステータスの流れ: `Proposed`（提案・判断待ち）→ `Accepted`（採用）→ `Deprecated`（廃止）または `Superseded by ADR-NNNN`（置き換え）。
採用後に内容を変えるときは、上書きせず新しい ADR を書いて古いほうを `Superseded` にする。

実装計画（`docs/plans/`）からは該当 ADR を番号で参照する。計画は機能単位、ADR は判断単位。
