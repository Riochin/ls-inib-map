# ADR-0009: 台数の上書きに「その時点の公式台数」を添え、公式が変わったら上書きをやめる

- 日付: 2026-11-18
- ステータス: Accepted
- 関連: ADR-0008、`src/lib/apply-overrides.ts`、`src/types/overrides.ts`、`scripts/merge.ts`、`src/data/overrides.json`

## 背景

- 公式サイトの台数がライブモニター込みで多めに載っている店は、`overrides.json` の `machineCounts` で実際に遊べる台数に直している（例: 公式5台 → 上書き4台）。
- 上書きは、公式の値がいくつであっても適用される（`applyOverrides`）。上書きには「どの公式値を見て直したか」が残っていない。
- そのため、公式が減台して 5台→2台 になっても、地図には上書きの4台が出続ける。公式で台数が載らなくなった場合（0台＝台数不明として落とす）も同じで、4台のまま出る。
- 店が公式一覧から消えた場合は `delisted` になり、両ゲーム設置店で片方のゲームだけ消えた場合はそのゲームの台数バッジが出なくなるので、問題は起きない。抜けているのは、**一覧に残ったまま台数だけが変わる場合**。
- 2026-11-18 時点で店舗 771、上書き 173 件、そのうち台数を持つものが 97 店・121 件（店×ゲーム）。公式と比べると、上書きのほうが少ないもの 72 件、同じ値 44 件、多いもの 1 件、公式に台数が無いもの 4 件。同じ値の 44 件は、台数を運営確認済み（確定表示）にするための上書き。
- 減台は、来店して初めて気づくことが多く、ユーザー報告では拾いにくい。公式の値が変わったことは週次の更新で分かるが、今はそれを上書きと照らし合わせていない。

## 決定

台数の上書きに **上書きした時点の公式台数**（基準値）を添え、公式の現在値が基準値と違ったら、そのゲームの台数の上書きを適用しない。

- 基準値はゲーム別に持つ（`machineCounts` と同じ形）。公式に台数が無かったときは 0 を入れる
- 基準値は、管理画面での保存時とユーザー報告の自動反映時に、その時点の `stores.json` の値から書き込む。人が手で入れるものにしない
- 適用時（`applyOverrides`）に、公式の現在値と基準値を比べる。違えば台数の上書きを飛ばし、公式の値と出どころ（未確認）をそのまま出す。減っても増えても同じ扱いにする
- 飛ばした上書きは消さずに残し、週次の更新で一覧にして知らせる。運営が見直して上書きを保存し直せば、基準値が新しい公式値に更新され、再び適用される
- 基準値を持たない既存の 121 件は、導入時に現在の `stores.json` の値で一度だけ埋める
- 台数以外の上書き（営業時間・フロアなど）はこの判定の対象にしない

理由:

- 上書きは「公式がこの値のとき、実際はこう」という公式値を前提にした補正なので、公式値が変われば前提が崩れる。新しい公式値のほうが、古い補正より新しい事実に近い
- 見直しまでの間も、古い4台ではなく公式の2台（未確認表示）が出る。間違った台数を確定のように出し続けるより安全
- 取得に失敗したサイトの台数は前回値を引き継ぐので（ADR-0008）、取れなかった週に誤って上書きが外れることはない

## 検討した選択肢

### 案B: 公式値が上書きより小さくなったら公式を優先する（基準値を持たない）

- 概要: 公式2台 < 上書き4台 のように、公式が上書きを下回ったときだけ公式を採る。
- 利点: フィールドを足さずに済み、既存データの移行も要らない。
- 欠点 / リスク: 公式 5→4 の減台（実際は 4→3）のように、上書きを下回らない変化を拾えない。増台も拾えない。上書きのほうが多い店（1件）では逆に働く。
- 却下理由: 「公式が変わった」ことではなく「値の大小」を見ているので、減台の多くを見逃す。

### 案C: 基準値は持つが、ずれたら知らせるだけで上書きは適用し続ける

- 概要: 判定は案Aと同じで、表示は上書きのまま。週次の Issue で見直しを促す。
- 利点: 公式の見せ方だけが一時的に変わった場合でも、表示が揺れない。
- 欠点 / リスク: 見直すまで、古い台数が確定表示で出続ける。1人運用なので、見直しが数週間遅れることがある。
- 却下理由: 一番避けたい「減ったのに多く出る」状態が、見直しの速さ次第で続いてしまう。

### 案D: 台数の上書きに有効期限を付ける（`updatedAt` から N 日で失効）

- 概要: 一定期間たった上書きを自動で外す。
- 利点: 判定が単純で、公式の値を見なくてよい。
- 欠点 / リスク: 公式が変わっていなくても期限で外れ、正しい補正（ライブモニター分を引いた台数）が定期的に消える。公式が変わっても期限までは外れない。
- 却下理由: 外れるきっかけが公式の変化と関係ない。

### 案E: 今のまま、ユーザー報告で直す

- 概要: 仕組みは変えず、減台の報告が来たら上書きを直す。
- 利点: 何もしなくてよい。
- 欠点 / リスク: 減台は来店して気づくもので、報告されにくい。公式が変わったことは分かっているのに使っていない。
- 却下理由: 手元にある情報で防げる誤表示を放置することになる。

## 影響

- 楽になる: 公式の減台・増台が、上書きのある店でもそのまま地図に出る。見直しが必要な上書きが週次で一覧になるので、どこを確認すればよいか分かる。
- 難しくなる: 上書きのデータに基準値が増え、管理画面と自動反映ワークフローの両方で書き込む必要がある。公式が台数の数え方を全体で変えたときは、上書きが一斉に外れて未確認表示に戻る（データは残るので、見直して保存し直せば戻せる）。
- 見直しの目安: 外れた上書きの見直しが毎週の負担になるほど多い（目安として週10件を超える）なら、自動で外さず知らせるだけにする案C に寄せるか、店ごとに「公式との差（例: −1台）」で持つ形を検討する。
