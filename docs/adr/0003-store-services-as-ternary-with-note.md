# ADR-0003: クレジットサービス・貸切はゲーム別の三値＋ゲーム別の自由記述で持つ

- 日付: 2026-10-10（同日中に「店単位」→「有無のみゲーム別」→「有無も内容もゲーム別」と2回改訂。未マージのため新 ADR ではなくその場で改訂）
- ステータス: Accepted
- 関連: Issue [#35](https://github.com/Riochin/ls-inib-map/issues/35)、[画面モック](https://claude.ai/artifact/8bxiJxzwSEPmRtxZvertLy)（「サービスの内容: ゲームごと」が採用案）、ADR-0002

## 背景

- クレジットサービス（100円2クレなど）や貸切の有無を店舗情報に載せたい要望がある。公式サイトからは取れず、利用者の報告（UGC）前提。
- 中身が店ごとに違う。クレジットサービスは曜日や時間帯の条件があり、貸切は「1時間いくら」「1台いくら」「1人いくら」と単位がそろわない。
- 値段や条件は変わりやすく、古くなった情報が正しそうに見えると害が大きい。
- ゲームによって対応も内容も違う店がある（イニブは100円2クレ、ラスサバは100円3クレなど）。設置店 770 のうち両ゲーム設置店は 230。
- 「無制限台は台数も、クレジットサービスは詳細も、貸切は値段も欲しくなる」という要望があり、どこまで構造化するかが論点。
- 当初は「ゲーム別にすると両ゲーム店で『ゲームで違う』切り替え UI が要る」と考えて店単位にしたが、録画台・配信台は切り替えなしで2列を並べているだけで、同じ形にすれば切り替えは不要だと分かった。
- 次に「有無はゲーム別、内容は店で1つ」としたが、提供フォームのモックで比べたところ、内容もゲームごとに書けるほうが報告者にとって自然だった。1文に2ゲーム分を詰めると「イニブは〜、ラスサバは〜」と書き分ける負担が報告者側に移る。

## 決定

クレジットサービスと貸切を **ゲーム別の三値＋ゲーム別の自由記述** で持つ。

- 有無: `creditServiceByGame` / `rentalByGame`（ゲーム別 `あり / なし / 不明`。`hasRecordingByGame` と同じ型・同じマージ規則）
- 内容: `creditServiceNoteByGame` / `rentalNoteByGame`（ゲーム別の自由記述・各100文字まで。`floorByGame` と同じ型）。そのゲームが「あり」のときだけフォームに欄を出す
- 出どころ（確定／未確認）は三値に付ける（`attributeSources.creditServiceByGame` など）。自由記述は補足（`remarks`）と同じ中立表示で、確定／未確認の対象外
- 絞り込みの対象にはしない。詳細モーダルに「店のサービス」の枠で、「ラスサバ あり ／ イニブ あり（未確認）」の行とその下にゲーム名つきの内容を1行ずつ表示する。片方だけの店はゲーム名なし
- フォームは、内容を持つため2列に詰めず **「ラスサバ、内容、イニブ、内容」の順に縦に並べる**。片方だけの店は「イニブ、内容」のみ。有無だけの録画台・配信台・無制限台は従来どおり2列
- 自由記述は既存の報告経路（フォーム → Issue → 自動反映の PR → 人のレビュー）を通る。自動反映ワークフローの指示文に「SNS ID 等を除いた中立な1文に整えてゲーム別の専用欄へ入れる。補足欄には入れない」を追加する

理由:

- 有無をゲーム別に持てば、将来「イニブでクレジットサービスがある店」と絞り込みたくなったときに構造で答えられる。文章に埋めると取り出せない。
- 内容もゲーム別にすると、報告者は目の前のゲームのことだけを書けばよい。「イニブは〜、ラスサバは〜」と1文に書き分ける負担を利用者に負わせない。
- ゲーム別の文章は `floorByGame` と同じ型で、既存のゲーム別マージ・表示整形がそのまま使える。
- 値段や条件は形がそろわないので、分けて持っても絞り込みに使えない。文章なら「参考情報」として読まれ、古くなったときの害が小さい。
- 三値を残すことで「この店にはクレジットサービスはない」という報告を受け取れる。

## 検討した選択肢

### 案B: 店単位の三値＋店で1つの自由記述（最初の決定）

- 概要: `creditService` / `rental` を店で1つの三値にし、ゲームの違いは文章に書く。
- 利点: フィールドが少ない。
- 欠点 / リスク: 「イニブだけ対応」が構造に残らず、将来ゲーム別に絞り込めない。両ゲーム店の報告者が「どちらのゲームの話か」を文章で補う手間が増える。
- 却下理由: 店単位にした理由（切り替え UI が要る）が誤りだった。ゲーム別にしても録画台と同じ形で済む。

### 案C: 有無はゲーム別、内容は店で1つ（2回目の決定）

- 概要: `creditServiceByGame` はゲーム別三値、`creditServiceNote` は店で1つの文章。
- 利点: フィールドが案Dより2つ少ない。両ゲーム共通の条件（「平日の18時まで」）を1回書けば済む。
- 欠点 / リスク: ゲームで内容が違うとき、報告者が1文に「イニブは〜、ラスサバは〜」と書き分ける必要がある。表示も1文に2ゲーム分が混ざる。
- 却下理由: フォームのモックで比べ、ゲームごとに欄を分けたほうが報告者にとって自然だった。共通条件を2回書く手間は小さい。

### 案D: 料金・単位・条件を個別の欄に構造化する

- 概要: 貸切は「料金」「単位（時間／台／人）」「予約要否」、クレジットサービスは「レート」「曜日」「時間帯」を別フィールドで持つ。
- 利点: 表示をそろえられる。将来「貸切 3,000円以下」のような絞り込みができる。
- 欠点 / リスク: 単位の組み合わせが店ごとに違い、欄が増えるほどフォームが長くなる。きれいな欄に入った古い値段は正しく見える。
- 却下理由: 絞り込みに使う見込みがなく、入力負担と陳腐化リスクだけが増える。

### 案E: 専用フィールドを作らず補足（remarks）に書く

- 概要: 「100円2クレあり」などを既存の補足欄に運営が書く。
- 利点: 型もフォームも変えない。
- 欠点 / リスク: 「なし」を表せない。他の補足と混ざって一覧性が無い。フォームに項目が無いので報告が集まらない。
- 却下理由: 項目として存在しないと要望に答えたことにならない。

## 影響

- 楽になる: 有無は録画台、内容はゲーム別フロアの複製で、新しい型は増えない。ADR-0002 の無制限台と合わせ、ゲーム別三値の項目が5つ（録画台・配信台・無制限台・クレジットサービス・貸切）になり、フォームと表示の作りがそろう。
- 難しくなる: フォームの中で「2列（有無だけ）」と「縦積み（有無＋内容）」の2つの並べ方が共存する。自由記述の公開には整形ルールが要り、自動反映ワークフローの指示文（`.github/workflows/reflect-user-reports.yml`）の変更は main に載ってから手動実行で確かめる必要がある。
- 見直しの目安: 「貸切の値段で探したい」要望が複数来たら案Dの一部（料金のみ）を再検討する。両ゲーム店で内容が同文の報告ばかりなら、案Cへの簡略化を検討する。
