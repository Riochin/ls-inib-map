# ADR-0006: kiro スペック駆動をやめ、plan mode＋ADR＋計画文書で進める

- 日付: 2026-10-10
- ステータス: Accepted
- 関連: ADR-0001、`CLAUDE.md`、`.claude/skills/lsib-adr/`、`.claude/skills/lsib-plan/`、過去のスペック `.kiro/specs/`（6件）

## 背景

- ver2.0〜2.5 は kiro 流のスペック駆動（`/kiro:spec-init` → 要件 → 設計 → タスク → 実装、各段階で人の承認）で進めてきた。`.kiro/specs/` に6機能分のスペックが残っている。
- 開発は本人1名と Claude Code の組み合わせで、要件・設計・タスクの3文書をそれぞれレビューして承認する工数が、実装そのものより重くなっていた。承認を `-y` で飛ばすと3段階の意味が薄れる。
- 一方で「なぜそう決めたか」が残らない問題は ADR-0001 で解決し、「どこを・どの順で触るか」は計画文書（`docs/plans/`）として残せるようになった。スペックが担っていた役割のうち、残す価値があるのはこの2つだった。
- Claude Code の plan mode は、実装前に進め方を会話で詰めて1回承認する流れで、承認は1段階で済む。

## 決定

kiro のスペック駆動を **使わない**。代わりに次の3点で回す。

- **判断は ADR**（`docs/adr/`）。データの持ち方・層の分け方・運用ルール・代替案を捨てた UX 方針を、実装前に残す
- **作業は plan mode**（`/plan`）。実装前に進め方を詰め、1回の承認で実装に入る
- **記録は計画文書**（`docs/plans/YYYY-MM-DD-<feature>.md`）。承認された計画を、触るファイル・順序・コミット分割・確認手順の形で残す。実装後に差分があれば「実装後の変更」を追記する

残すもの: steering（`.kiro/steering/`）はプロジェクト知識として引き続き使う。過去のスペックは履歴として残す。`.claude/commands/kiro/spec-*` は削除せず、呼ばない。

理由:

- 承認が3段階から1段階になり、レビュー工数が実装に見合う量になる。
- 「なぜ」（ADR）と「どこを・どの順で」（計画）が別文書で残るので、スペックを捨てても後から追える情報は減らない。
- 計画文書は実装後も更新する前提なので、スペックのように「実装が終わると参照されない」文書にならない。

## 検討した選択肢

### 案B: kiro スペック駆動を続ける

- 概要: 現状維持。要件・設計・タスクを毎機能で書き、各段階で承認する。
- 利点: 文書が揃う。要件の抜けを設計前に見つけやすい。
- 欠点 / リスク: 1人開発では承認がボトルネック。3文書の整合を保つ手間が機能追加のたびにかかる。
- 却下理由: レビュー工数が実装を上回っており、続ける動機が無い。

### 案C: kiro を `-y`（自動承認）で高速化して続ける

- 概要: 要件・設計・タスクの生成は続け、承認だけ省く。
- 利点: 文書は残る。コマンド体系を変えない。
- 欠点 / リスク: 承認を省いた3文書は読まれないまま実装に進み、形式だけが残る。生成コストと保守コストは変わらない。
- 却下理由: 「読まない文書を生成する」工程になる。

### 案D: plan mode だけで文書を残さない

- 概要: 会話で詰めて承認し、文書は書かない。
- 利点: 最も軽い。
- 欠点 / リスク: セッションをまたぐと計画も判断も失われ、同じ議論を繰り返す（ADR-0001 の背景と同じ問題）。
- 却下理由: 「なぜ」と「どこを」は残す価値がある。文書2種に絞れば負担は小さい。

## 影響

- 楽になる: 機能追加の前段が「ADR（必要なら）→ plan mode → 計画文書」の3手で済む。承認は1回。
- 難しくなる: 要件の抜けを設計前に拾う工程が無くなる。plan mode の会話で要件の確認を兼ねる。計画文書の体裁は `lsib-plan` スキルで固定して、ばらつきを抑える。
- 見直しの目安: 計画文書が実装後に更新されず放置される機能が続いたら、計画の粒度か更新の運用を見直す。複数人開発になったら承認段階を増やすか再検討する。
