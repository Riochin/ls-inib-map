# ADR-0001: 設計判断を ADR として記録する

- 日付: 2026-10-10
- ステータス: Accepted
- 関連: [docs/adr/README.md](README.md)、[docs/feedback-flow.md](../feedback-flow.md)

## 背景

- ver2 系で店舗属性（営業時間・フロア・録画台・配信台など）を増やしてきたが、「なぜこの持ち方にしたか」はチャットの会話、PR 本文、Issue コメント、kiro スペックの design.md に散っていた。
- ver2.6 以降も無制限台・クレジットサービス・貸切と項目追加が続く見込みで、「サービスとして一括りにしなかった理由」のように、後から同じ議論を繰り返しやすい判断が増えている。
- 開発は本人1名と AI の組み合わせで、セッションをまたぐと AI 側の文脈が失われる。判断の理由がリポジトリ内に無いと、同じ案を再提案したり、過去に捨てた案を採用しかける。

## 決定

`docs/adr/` に軽量な ADR（1判断＝1ファイル、[template.md](template.md)）を置き、設計判断をそこに記録する。

理由:

- リポジトリ内にあるので、人も AI も同じものを読める。セッションをまたいでも文脈が残る。
- 「検討した選択肢」と「却下理由」を必須にすることで、採用案の説明だけで終わらない。
- kiro のスペックは機能単位で、機能をまたぐ判断（データの持ち方の原則など）の置き場所が無かった。ADR は判断単位なのでそこを埋められる。

## 検討した選択肢

### 案B: kiro スペックの design.md に書く

- 概要: 各機能の設計書に「判断と理由」の節を設け、そこに書く。
- 利点: 新しい置き場所を作らない。機能の文脈と一緒に読める。
- 欠点 / リスク: 判断がスペック単位で散る。機能をまたぐ判断（三値の持ち方、確定/未確認の扱い）の正本が無い。スペックは実装が終わると参照されにくい。
- 却下理由: 「後からなぜを探す」用途に向かない。（追記: ADR-0006 で kiro スペック自体を使わなくなった。計画文書から ADR を参照する形に置き換え）

### 案C: Issue コメントに残す

- 概要: 該当 Issue のコメントに判断と理由を書く。
- 利点: 要望との距離が近い。追加作業が少ない。
- 欠点 / リスク: 検索しにくい。ステータス（採用・廃止・置き換え）を管理できない。Issue が閉じると埋もれる。
- 却下理由: 時系列の記録には向くが、現在有効な判断の一覧にならない。

## 影響

- 楽になる: 設計の相談のとき、過去の判断を前提にして話を始められる。AI への指示も「ADR-0003 の方針で」と短くできる。
- 難しくなる: 判断のたびに1ファイル書く手間が増える。書く対象を README で絞り、細部は対象外にして負担を抑える。
- 見直しの目安: ADR が20件を超えて一覧が見づらくなったら、分類（データ・運用・UX）を入れる。
