# lsib-adr: 設計判断を ADR に残す

## Overview

このリポジトリの設計判断は `docs/adr/` に1判断＝1ファイルで残す。目的は「何を選んだか」ではなく **「なぜ他の案を捨てたか」** を後から読めるようにすること。会話で決まっただけの判断は、実装前に必ずファイルにする。

## When to Use

- データの持ち方を決めた（新フィールド、ゲーム別か店単位か、三値か文章か）
- 層の分け方・責務の置き場所を決めた
- 運用ルール（ワークフロー、レビューの通し方、公開範囲）を決めた
- UX の方針で、代替案を比べて捨てた
- 判断待ちの提案を出す（ステータス `Proposed` で置く）

使わない: 実装の細部、1ファイルで完結する命名、一時的な作業手順。

## 手順

1. `docs/adr/README.md` の一覧で次の番号を確認する（4桁連番）
2. `docs/adr/template.md` をコピーして `docs/adr/NNNN-<english-kebab-slug>.md` を作る
3. 各節を埋める。**背景には数字・実データ**（店舗数、記入率、該当 Issue の件数）を入れる
4. **検討した選択肢は最低2つ。** 却下理由を1行で言えない案は検討不足
5. **影響** に「楽になる／難しくなる／見直しの目安」を書く
6. README の一覧に1行足す
7. 実装計画（`docs/plans/`）があれば、計画の「関連」から ADR 番号で参照する
8. コミットは `docs(adr): …` で単独にする

## ステータスの扱い

| 状況 | すること |
|---|---|
| 判断待ちの提案 | `Proposed` で置き、採否が出たら `Accepted` に書き換えて再コミット |
| マージ前に判断が変わった | **その場で改訂**し、日付の行に「同日中に〜から〜へ改訂。未マージのため新 ADR ではなくその場で改訂」と残す。旧案は却下案として理由つきで残す |
| マージ後に判断が変わった | 新しい ADR を書き、古いほうを `Superseded by ADR-NNNN` にする。上書きしない |

## 書き方の注意

- 日本語。文体は README・既存 ADR にそろえる
- タイトルは「何を・どう持つ／分ける／運用する」が分かる文（例「無制限台は『台の種類』としてゲーム別に持つ」）
- 却下理由が後で誤りだと分かったら、それ自体を背景に書く（「当初〜と考えたが、〜で不要と分かった」）。判断の履歴が価値
- 用語はアプリの表示語に合わせる（「クレジットサービス」「ラスサバ」「イニブ」）

## Common Mistakes

- 会話で決めて満足し、ファイルにしない → 次のセッションで同じ議論を繰り返す
- 採用案だけ書いて却下案を省く → 「なぜこうなった」に答えられない
- 括りの基準を説明できないまま分類する（「サービス」に無制限台を入れた例）→ 基準を一文で書けるか確かめる
- ADR に実装手順やファイル一覧を書く → それは `lsib-plan` の領分
